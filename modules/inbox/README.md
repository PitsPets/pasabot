# @pasabot/mod-inbox (W35)

A bot inbox and an email bridge between two PasaBot bots.

- **Guided mailbox step** (Inbox page): the owner creates the mailbox at any provider, in their own browser, and turns on IMAP/SMTP and an app password there. PasaBot asks only for the address, IMAP/SMTP host, port and security (TLS from the start, or mandatory STARTTLS) and the app password, and keeps all of it in the vault (scope `inbox`: `mailbox_settings`, `mailbox_app_password`). Nothing about the mailbox is stored in a module table, event or log. The stored app password is reused on an edit only while the IMAP/SMTP hosts, ports and user name stay the same; pointing the mailbox anywhere else needs the app password typed again (`400 password_required`), so the vault-held password never goes to a new server unasked. PasaBot never creates a mailbox, never signs in through a browser and never solves captchas; no provider is pre-filled.
- **Network**: `safeConnect` from `@pasabot/safe-net` reaches only the owner-entered host of each protocol, pins the resolved address, refuses blocked addresses, and always signs in over verified TLS (`requireTls()`). A server that does not offer STARTTLS is refused, never used in plaintext. Plaintext bytes that arrive after the STARTTLS reply are refused, never read as if they came over TLS (STARTTLS injection). Hosts that may resolve to private addresses (a mail server on the LAN, a local bridge app) come only from operator config: `PASABOT_INBOX_PRIVATE_HOSTS=host1,host2`. No tool can set or change a host.
- **Mail is untrusted data**: listed on the Inbox page as plain text (HTML converted to text, remote images never loaded). Agents read it only through `inbox_list` / `inbox_read`, and only on the owner's own turns (or agent-to-agent work whose chain the owner started): a run never reads more than the person who started it could (ARCHITECTURE 7.1), so members, guests, channel senders, webhooks, automations and delegations from them get a refusal. Inside the labelled untrusted block, one-time codes, sign-in codes and verification links are masked by a linear scan (`src/mask.ts`). The owner sees them unmasked.
- **Sending**: `inbox_send` (new mail, `inReplyTo`, `forward`, blob attachments) and `inbox_bridge_send` are `actionClass: 'outbound-message'` with `noAlwaysAllow`. The core gateway raises the card (to, cc, bcc, from-address, subject, body preview, attachment names and sizes, plus the exact request) at every trust tier; nothing is sent before the owner approves it in the app.
- **Email bridge** (`src/bridge.ts`): each bot has an Ed25519 key (private key in the vault). Owners exchange address + public key on the Inbox page and pin each other. A bridged mail carries `X-PasaBot-Bridge: v1.<envelope>.<signature>` over sender bot, recipient bot, thread id, nonce, timestamp and body hash. A wrong From address or key, an unsigned or altered envelope, a stale timestamp (±10 min) or a reused nonce is refused; refused messages show on the Inbox page with the reason and are never offered to agents. A verified message is still untrusted data.
- Mail is checked every 5 minutes while a mailbox is set up (skipped while the W31 stop is on), or with "Check for new mail".

Tests: `vitest run modules/inbox packages/safe-net` (fake IMAP/SMTP server in `src/testing/`, 127.0.0.1 port 0, a throwaway certificate made with the `openssl` CLI), `pnpm --filter @pasabot/mod-inbox test:e2e` (1440 and 390 px; needs `apps/web/dist`).
