# @pasabot/provider-opencode

`ProviderAdapter` for the OpenCode CLI (`opencode run --format json`, one process per turn, prompt on stdin).

- Maps the JSON events to ProviderEvents: the first `sessionID` → session, reasoning → thinking, each text part → one text delta (parts arrive whole), `tool_use` → tool call + result, `step_finish` tokens summed into one usage (reasoning counted as output, cache read + write as cache), `error` → classified error (auth by error name, 429 → rate limit, reset time when stated). The final text is the last step's text. Exactly one `done`.
- Resume: `--session <id>`. A reseed (provider switch / compaction) goes ahead of the user text in a new session as an `<earlier-conversation>` block; wrapper tag names inside untrusted text are defused (`<` → `&lt;`) so they cannot close or forge a block (ARCHITECTURE 8).
- Per-turn config, in two layers:
  - Security settings in `OPENCODE_CONFIG_CONTENT`, OpenCode's highest-precedence layer, so no config file can override them: the system prompt (as an `instructions` file, rewritten every turn), permissions per effective trust, `share: "disabled"` (a session is never published to a share link), `autoupdate: false`, `plugin: []`.
  - Only the PasaBot MCP gateway entry with the run bearer goes in a 0600 JSON file in `<workspace>/.pasabot/`, named by `OPENCODE_CONFIG` and removed after the turn (the bearer is never on the command line or in the environment the agent's shell inherits).
  - `OPENCODE_DISABLE_PROJECT_CONFIG=1`, so an `opencode.json` or `.opencode/` the agent wrote into its workspace cannot add MCP servers, plugins or permissions; an inherited `OPENCODE_CONFIG_DIR` / `OPENCODE_PERMISSION` is dropped.
  - Without a provider account, `XDG_CONFIG_HOME` is a fresh empty folder per turn (removed after), so the owner's own `~/.config/opencode` (personal MCP servers, plugins, providers) never loads into an agent turn. Login lives under the data folder and is unaffected.
- No permission bridge in `run` mode, so whatever PasaBot would ask about is denied. The turn's **effective** trust is the lower of the agent's and the sender's trust, one level lower for any sender but the owner (ARCHITECTURE 7.1, 7.4), so a non-owner turn is never `trusted`. Workspace edits allowed (tier 1), shell and web fetch only for a `trusted` turn (tier 2), anything outside the workspace denied (tier 3). Tool-less calls (`tools: 'none'`) deny everything and get no gateway.
- Runner sandbox: every spawn goes through `TurnInput.sandbox` with OpenCode's XDG data/config/cache/state folders writable (the config one is the per-turn folder when there is no account). Without an account every XDG home (data, state, cache, config) is inside PasaBot's own data: the agent's workspace for a turn, `$PASABOT_HOME/providers/opencode` for the model list, so nothing is written to the user's `~/.local/share/opencode` or `~/.cache/opencode`. A provider account points `XDG_DATA_HOME` / `XDG_CONFIG_HOME` / `XDG_STATE_HOME` / `XDG_CACHE_HOME` under its config dir.
- `listModels` reads `opencode models`. `steer` is not offered (`run` reads the prompt once). `skillsDir` = `<workspace>/.opencode/skill`.

Tests replay a recorded-format stream (`src/__fixtures__/stream.jsonl`) through a stand-in CLI, so they need no network or account. Live run on a developer machine: `PASABOT_LIVE=opencode pnpm test:live`.
