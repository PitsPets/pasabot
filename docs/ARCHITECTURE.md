# PasaBot architecture

PasaBot is a self-hosted, local-first workspace where a team of AI agents (each one backed by an external agent CLI) chat with the owner, with each other and with outside chat apps, run on schedules, and use tools. One server process, one SQLite database, one web client (PWA) that is also the phone client in v1.

Status: pre-alpha design. This file is the contract every workstream builds against. Changing anything in sections 2–6 is an **interface change** (see ROADMAP.md, "Collision rules").

---


The chat log keeps every run event whose type it does not draw itself (anything but tool calls/results, permissions, text, thinking, usage, session, error, done) and hands it to the matching `runEventRenderers` entry, live and after a reload (`GET /api/v1/runs/:id/activity`). A person's own message renders its blocks under the bubble too (file previews). Live events the shell does not keep (module events, `reaction.changed { chatId, messageId }`, which `ChatPort.react` publishes on `chat:<id>`, and every `live` WS frame but `message.delta`, e.g. `browser.frame`) are re-dispatched on `window` as `CustomEvent(LIVE_EVENT = 'pasabot:event', { detail: { type, data } })` for module components.

Discovery: the server scans workspace and `node_modules/@pasabot/*` for `package.json` with `"pasabot": { "kind": "module" | "provider" | "channel" | "plugin", "entry": "./dist/server.js", "web": "./web/index.tsx" }`. No central registry file. Web: `import.meta.glob('/../../modules/*/web/index.tsx')` and the same for `plugins/*/web` and `providers/*/web` (a provider package that is also a module, e.g. W34's `providers/local`; its locales merge the same way); each exports a `WebModule` and the shell renders every slot. Locales: `*/locales/<code>.json` (any language, found by glob; a module loads its own with `localeResources` from `@pasabot/i18n` and follows `<html lang>` via `documentLocale()`), merged under namespace `<id>`. `messages.blocks` is an array of `{ kind: '<module>.<kind>', v, data }`; unknown kinds render as a plain fallback card. **`modules/_example`** fills every server and web slot (one route per auth kind, a public hook, a sites file, a table, a tool, an event, a block, a page, a locale) and is W0a's proof that the SDK works.

### 2.2 SDK details settled by W0a

- `ModuleHost` also carries `id` and `dataDir` (`$PASABOT_HOME/modules/<id>`). Ports whose implementation lands later (`vault`, `net`, `files`, `approvals` before W0b) throw `PortUnavailableError` on use; they are never silent no-ops.
- Routers: `http.route({ method, url, auth, body?: zod, bodyLimit?, handler(ctx) })`, `auth` = one kind or a list of `session`/`automation`/`run`; a request whose principal kind is not accepted gets 401. `publicHttp.route({ method, url, rateLimit: { max, windowMs }, bodyLimit, handler(ctx) })`; the limit runs before the body is read (429 + `Retry-After`, 413 over `bodyLimit`) and `ctx.rawBody` holds the exact bytes. Handlers return JSON, or `httpResponse(status, body, headers)`, or throw `HttpError`.
- `sitesOrigin.put(path, data, contentType)` serves at `<sites origin>/<module id>/<path>` from `$PASABOT_HOME/sites/<module id>/`; every sites response carries `CSP: sandbox allow-scripts` and `nosniff`.
- Names: module tables/indexes/triggers start with `<id>_` (checked by the migration runner); tools start with the id minus leading underscores (`_example` -> `example_echo`), except the gateway meta-tools `tools_find`/`tools_describe`/`tools_invoke` (5.4), which only the `mcp` module may register (`GATEWAY_META_TOOLS`, `mayRegisterTool`); block kinds start with `<id>.`.
- Discovery: the `pasabot` field may also name `"source": "./src/server.ts"`, used when the built entry is missing or in dev/test runs (`PASABOT_SOURCE=1`, Vitest). Workspace packages export a `source` condition so tests and typecheck run on TypeScript sources without a build.
- Discovery root: `PASABOT_ROOT`, else the pnpm workspace holding the server code, else the install prefix whose `node_modules/@pasabot` holds it; never the process cwd. Boot logs a warning when discovery finds no packages. `channel` packages are registered in the `ChannelRegistry` at boot.
- `@pasabot/core/web` component types are framework-neutral functions; the shell renders them with React. Module web code may `import type` from `@pasabot/core/web`.

### 2.3 Security details settled by W0b

- `ToolDef.widens?: boolean` marks a widening tool (7.4). The `/mcp` gateway never lists or invokes one; widening stays owner-session REST.
- `TurnInput.sandbox?: CommandWrapper` (`(cmd, args, opts?: { writable?: string[]; readable?: string[] }) => { cmd, args }`): adapters pass every CLI spawn through it. `writable` names the CLI's own state outside the workspace (Claude: `$CLAUDE_CONFIG_DIR`, else `~/.claude` + `~/.claude.json`); existing paths are bound read-write under bubblewrap (Seatbelt already allows writes outside the denied trees), and a path inside or containing a protected tree ($PASABOT_HOME, the `pasabot` CLI credential folder, `~/.ssh`, keychains, browser profiles) makes the wrapper throw. `readable` names install folders below a module's data dir (`$PASABOT_HOME/modules/<id>/<sub>/...`, e.g. a registry-installed ACP agent's `agents/<id>`) that the CLI may read and execute but never write (Seatbelt re-allows reads there; bubblewrap `--ro-bind`s them inside the hidden home); any other readable path makes the wrapper throw. Every keychain file stays denied, the login keychain too: it holds every app's items (the vault master key among them) and anything the agent runs inherits the sandbox. On macOS the Claude adapter reads its CLI's own login item (`Claude Code-credentials`) in the server process, outside the sandbox, and hands the CLI only the access token as `CLAUDE_CODE_OAUTH_TOKEN` (`sandboxLoginEnv`; never for a provider account or a login already in the env). The refresh token never enters the sandbox, so a sandboxed turn never refreshes or rewrites the login; an expired access token is not passed and that turn fails as `auth` until the owner's own Claude Code refreshes it (or a long-lived `claude setup-token` is used). The orchestrator builds it from the runner mode (7.2); it may throw when the mode cannot run here. `user` and `container` refuse to run until W20 ships their launchers, never falling back to unsandboxed.
- Origin rule (4.1): a WS upgrade or any non-GET request whose `Origin` is not an allowed origin gets 403 (`Origin: null` on a WS upgrade too). The comparison is the full `scheme://host:port`, never the host alone. Allowed origins: `PASABOT_ALLOWED_ORIGINS` (exact origins, e.g. a dev web server), the public URL's origin, this server's own port on every allowed host (http and https), and `https://<configured host>` (a TLS front on 443). The sites origin is never allowed, whatever the config says. Requests without `Origin` (CLI, native clients) pass this check; the Host allowlist still applies to them. Automation tokens are refused whenever an `Origin` header is present.
- Automation tokens, W0b part (`apps/server/src/auth/automation.ts`): issue (hash only, trust ≤ `standard`, optional expiry, `remote_ok`, `rate_per_hour` default 30), revoke, the resolver guards (Origin header refused, loopback unless `remote_ok`, expired/revoked/archived-agent tokens dead, `last_used_at`), `automationSender` (`SenderInfo.kind = 'automation'`, never `owner`, so tier 2+ never auto-approve) and `automationRunBudget` (runs in the last hour counted from queue items tagged by `automationSource`, so it survives restarts). The REST surface (`/api/m/automation/*`: token CRUD under an owner session, `POST runs` answering 429 + `Retry-After` from the budget, poll/stream) and the agent CLI verbs are W21. Modules reach these helpers through `ModuleHost.automation` (`AutomationTokens`: `issue(actor, …)`, `revoke(actor, id)`, `get(actor, id)`, `list(actor, …)` (never the hash), `isActive(actor, id)`, `source(actor)` for the queue item, `budget(actor, tokenId)`). Only the module with id `automation` gets a working port (every other module's throws). Every call takes the acting principal (`AutomationActor` = `Principal` or `asSystem(reason)`) and the port checks it itself, like the ChatPort; a refusal throws `AutomationAccessError` (code `automation_forbidden`, 403 from a module route), so code holding the port can never act on another agent's tokens. `issue`/`revoke`/`list` need a live owner session (checked against `sessions`/`users`, not the object's shape); `createdBy` is that owner and issue/revoke write `audit_log` (`automation.token_issued`/`automation.token_revoked`). `get`/`isActive`/`budget` also take a token principal reading its own id (and its own agent) or `asSystem(reason)` (the queue's dispatch-time `admit`); members, agent runs and other tokens are refused. `source(actor)` takes the calling token's own principal and throws for a revoked, expired or other agent's token.
- QR pairing (8, "Pairing hijack"): `POST /api/v1/pairing` answers `{ code, codeId, expiresAt, fingerprint, publicUrl }`. `codeId` is a non-secret id derived from the code's hash; every claim carries the `codeId` of the code it used and `GET /api/v1/pairing/claims?codeId=` lists only that code's claim, so a client confirms the claim made on the code it showed, never an older one. `publicUrl` is the address the server advertises to phones (`PASABOT_PUBLIC_URL`, else its listen URL). A claim's `deviceName` (1–80) and `platform` (≤ 40) must be printable: control (C0, DEL, C1), format (bidi overrides, zero-width) and line/paragraph separator characters answer 400. `POST /api/v1/pairing` and `POST /api/v1/pairing/claims/:id/confirm` need a fresh re-auth (below), else 401 `reauth_required` and the claim stays pending; declining (`…/reject`) and listing claims never need it. A stale or stolen session therefore cannot pair itself a second device that outlives logout or revoking the first one. A confirm sends the same security notice as a new passkey, naming the device and platform (`pasabot pair` asks for the password, or reads `PASABOT_PASSWORD`, when the server answers `reauth_required`).
- The first-run setup link carries the token in the URL fragment (`<web>/#/setup?token=...`), so it never reaches a server log. Owner creation without a valid unused token is 403; with an owner present it is 409. Minting a token (at boot, by `pasabot setup-link`, or for the desktop window over the parent channel, 4.3) deletes every older unused one, so only one code is live at a time, and is refused once an owner exists.
- Vault master key: the OS keychain is used only when the caller asks for it (the `pasabot-server` entry does in macOS host mode without `PASABOT_VAULT_PASSPHRASE`); library and test boots never touch the keychain. Host modes without a keychain or passphrase leave the vault unavailable (`PortUnavailableError`) rather than writing `vault.key`. The keychain master key (`keychainMasterKey`) is minted only when `security find-generic-password` says the item is missing (exit 44, errSecItemNotFound); a locked keychain, a refused or cancelled prompt or any other failure leaves the vault unavailable for that run and the item untouched. A new key is added without `-U` (an existing item is never replaced) and is used only after it reads back from the keychain, so a data key is never wrapped under a master key the next boot cannot find.
- Attachments (iface for W7): `POST /api/v1/blobs` stores an upload (100 MB cap, 413 above). `POST /api/v1/chats/:id/messages` takes `attachments` (blob sha or `{ sha256, name, mime }`, ≤ 20; a blob the sender neither uploaded (`blob_uploads`, recorded from `BlobMeta.uploadedBy`) nor can already read in a chat it is attached in is 400 `unknown_blob`, more than 250 MB per message 413; observers get 403 `read_only`, the same rule as `ChatPort.canWrite`), stores `attachments` rows and passes `{ sha256, name, mime, size }` in the queue payload (the run executor copies each blob to `<workspace>/.pasabot/files/<runId>/<name>` and hands the CLI `TurnInput.user.attachments` as `LocalFile`s; `LocalFile.name` is the sanitised name on disk, never the sender's raw text; adapters whose CLI takes one prompt string add the list with `withAttachments(text, files)` from `@pasabot/core`, inside their untrusted quote, and it shows every path, name and type as a JSON string with control characters removed, so a name can never start a prompt line; a copy that fails is logged and the turn runs without files); it also takes up to 10 `blocks` of kinds registered with `blocks.register(kind, schema, { userAuthored: true })` (any other kind 400 `invalid_block`; a kind registered with `attachmentRefs` must name only this message's own attachments, same sha256/name/mime/size, else 400 `invalid_block`). `GET /api/v1/blobs/:sha` serves an attached blob to the owner or a reader of a chat it is attached in (else 404), always with `nosniff` and a `sandbox` CSP; only images/audio/video/pdf/plain text are inline, everything else (html included) downloads as `application/octet-stream`.
- A secret value pasted into a chat is redacted before storage, and the agent receives the redacted text (`[secret:name]`), consistent with reference-only secrets.
- Permission bridge: provider CLIs call the gateway tool `core_permission_prompt` (`{ tool_name, input }` -> `{ behavior: 'allow', updatedInput } | { behavior: 'deny', message }`). CLI tools are tiered by category: reads inside the workspace 0, writes inside it 1, shell/web/MCP 2, anything outside the workspace 3. A write into a CLI's own config folder in the workspace is 3 too: every provider's folder (`.claude/`, `.gemini/`, `.grok/`, `.codex/`, `.opencode/`, compared case-blind on the lexical and the real path) counts whichever provider the agent runs, since a settings file there (allowed tools, auto-accept, MCP servers, hooks) would let the CLI stop asking; an ACP edit/move/delete is tiered on every location it names (a move's destination too). The Claude adapter never lets the CLI read permission rules or hooks from the workspace: it loads only `user,project` setting sources (never `settings.local.json`), moves any `.claude/settings*.json` to `.pasabot/set-aside/` before each turn, and passes a locked `--settings` that denies file-tool edits of `.claude/**`, so no agent-written rule can act as an "always allow" that skips the bridge. The ACP adapter (Gemini, Grok, registry agents) does the same for every known CLI's project config: before each turn it unlinks a config folder that is a link and moves `.gemini/settings.json`, `.gemini/.env`, `.gemini/extensions`, `.grok/settings.json`, `.claude/settings*.json` and `.codex/config.toml` to `.pasabot/set-aside/` (skills folders stay), and refuses the turn if it cannot, so a file a low-trust turn planted (by an approved write or a shell command) is never loaded by a later turn's CLI.
- Pairing: the owner mints a code (120 s, single use); a device claims it and gets a claim secret; the owner confirms on an existing session; the device then exchanges the claim secret for a device-bound session. Pending claims live in memory (5 min). Minting a code and confirming a claim both need a fresh re-auth (2.4), because the device session is a new long-lived credential.

### 2.4 Web and auth details settled by W0c

- **Passkeys** (`apps/server/src/auth/passkey.ts`, WebAuthn via SimpleWebAuthn): `POST /api/v1/auth/passkey/register/{options,verify}` (signed-in user **with a fresh re-auth**), `POST /api/v1/auth/passkey/login/{options,verify}` (sets the session cookie; user verification `preferred`), `POST /api/v1/auth/passkey/reauth/options` (signed-in user; user verification `required`, only that user's credentials), `GET /api/v1/auth/passkeys`, `DELETE /api/v1/auth/passkeys/:id` (**fresh re-auth**). Adding or removing a passkey without a fresh re-auth answers 401 `reauth_required`: a passkey is itself a re-auth factor, so a stolen session must not be able to mint one; the first passkey of an account therefore needs the password. Both are audited (`passkey.added` / `passkey.removed`) and raise an in-app notification. The relying party is the page's own Origin, which must be an allowed origin (4.1); its hostname is the RP ID, so passkeys need a host name (`localhost`, a LAN/Tailscale name), never a bare IP. Challenges are single-use, in memory, 5 min, and bound to their purpose (a sign-in challenge is never accepted as a re-auth).
- **Re-auth** `POST /api/v1/auth/reauth` (`{ password }` or `{ passkey: { challengeId, response } }` from `reauth/options`, which must carry the UV flag: a touch without PIN/biometric is refused) marks the current session for 5 min (in memory, cleared on logout). A session just created by the password (setup, `POST /api/v1/auth/login`) starts re-authenticated for the same 5 min; passkey sign-in and pairing do not. **Approving a tier-3 approval** (`POST /api/v1/approvals/:id/approve`) without a fresh re-auth answers 401 `reauth_required` and the approval stays pending; deny never needs it (8, "Stolen device / session"). A computer-use card, and a sensitive card while a screen helper is active, need a re-auth made for that one card (`for: <approval id>`; 8.1 "Screen helpers vs approvals"), and every approve carries the card's `nonce`. Module routes see the same freshness as `principal.reauthed` on a session principal (true within those 5 min), so a module action that needs a fresh re-auth (W28 linking) answers 401 `reauth_required` without it.
- **Session token in bodies**: setup, login (password or passkey) and the pairing session return `token` in the JSON body only when the request has no `Origin` header (CLI, native clients). A page gets the `HttpOnly` cookie alone, so no script in the page can read the token.
- **Run activity** `GET /api/v1/runs/:id/activity` (session; 404 unless the caller can read the run's chat): the run's state/times and its `tool.call`, `tool.result`, `permission`, `subagent`, `error` events, for the chat's tool-activity line after a reload. Live updates still come from the `run:<id>` topic.
- **Web app** (`apps/web`): React 19 + Vite, hash routes (`#/setup?token=`, `#/login`, `#/pair?code=`, `#/chats/:id`, `#/agents/new`, `#/agents/:id/edit`, `#/devices`, `#/settings`, `#/settings/<group>`, `#/settings/<group>/<feature>`, `#/welcome`, `#/menu` (redirects to `#/settings`), and every module `RouteDef.path`; a module page that is a Settings feature renders inside the Settings frame with its group selected). ## 4. Protocol

### 4.1 HTTP

- REST under `/api/v1/*` (core) and `/api/m/<module>/*` (modules); zod in, zod out; OpenAPI at `/api/openapi.json`.
- Auth: `Authorization: Bearer <session|automation token>` or `HttpOnly; Secure; SameSite=Strict` cookie for the web. Tokens never in URLs.
- Mutations are REST. WS is push and streaming only (no RPC over WS) so every action is testable with plain HTTP.
- Agent tools: one MCP endpoint `/mcp` (streamable HTTP). Each run gets a run bearer: 256 random bits, stored only as a hash in `run_tokens`, bound to (run, agent), revoked on `done`, never derived from or equal to the run id. The provider adapter writes it into the CLI's MCP config.
- **Before auth, on every HTTP and WS request:** Host must be in the allowlist (configured hostnames + `localhost`/`127.0.0.1`/`[::1]`), else 421; the WS upgrade also requires an allowed `Origin`. This blocks DNS rebinding.
- **First run:** creating the owner needs a one-time setup token (printed to the console/log at first boot and by `pasabot setup-link`, single-use, 30 min expiry, one live code at a time). Without it `POST /api/v1/setup` → 403. No HTTP or WS route mints or returns a token; the desktop app (the macOS window, the Windows tray, the Linux starter) gets fresh ones only over the parent channel, or from the same-machine one-shot minter for a server it did not start (4.3).
- **Automation tokens** are accepted only on loopback unless the token has `remote_ok`; any request that carries an `Origin` header is refused before the token check; per-token rate limit (default 30 runs/h) → 429.
- **Owner-only widening:** routes that widen access (trust level, allowlists, per-tool "always allow", MCP levels, automation tokens, channel sender trust) require an owner session on REST and are never exposed as tools on `/mcp` (7.4).
- **Owner-only routes** (each module's `ownerOnly`: workflow runs and decisions, channel bindings and pairing, routines, memory review, collab team controls) check the session's `userKind === 'owner'`. A server has exactly one owner (3.1 `users_single_owner`), so that role check is also the resource-ownership check and no per-resource owner column is kept. Anything that would allow a second owner must first add per-resource checks to every such route.

### 4.2 WebSocket `/ws`

```ts
// client -> server
type C2S =
  | { t: 'hello'; v: 1; token?: string; resumeFrom?: number } // token only if no cookie
  | { t: 'sub'; topics: Topic[] }
  | { t: 'unsub'; topics: Topic[] }
  | { t: 'typing'; chatId: string }
  | { t: 'ping'; n: number };
// server -> client
type S2C =
  | { t: 'welcome'; serverId: string; seq: number; user: UserDTO }
  | { t: 'ev'; seq: number; topic: Topic; type: keyof EventMap; data: unknown } // persisted in `events`
  | { t: 'live'; topic: Topic; type: 'message.delta' | 'run.tick' | 'browser.frame'; data: unknown } // ephemeral
  | { t: 'gap'; from: number } // resume impossible -> client refetches via REST
  | { t: 'pong'; n: number }
  | { t: 'bye'; reason: string };
type Topic = 'global' | `chat:${string}` | `agent:${string}` | `run:${string}` | `module:${string}`;
```

Event map (extensible by module augmentation, so modules never edit the core file):

```ts
export interface EventMap {
  'message.created': MessageDTO;
  'message.updated': MessageDTO;
  'message.deleted': { id: string; chatId: string };
  'run.started': RunDTO;
  'run.finished': RunDTO;
  'run.event': RunEventDTO;
  'queue.changed': { agentId: string; items: QueueItemDTO[]; paused: boolean };
  'approval.requested': ApprovalDTO;
  'approval.resolved': ApprovalDTO;
  'agent.updated': AgentDTO;
  'agent.context': { agentId: string; used: number; window: number };
  notification: { level: 'info' | 'warn' | 'error'; text: string; href?: string };
}
// in a module:  declare module '@pasabot/protocol' { interface EventMap { 'routine.fired': RoutineFireDTO } }
```

Rules: `seq` is global and monotonic; clients store last seen seq; reconnect with `resumeFrom`; server replays from `events` or sends `gap`. Deltas are not persisted; the final `message.updated` carries the full text. Heartbeat every 25 s; server drops a client after 2 missed pongs. Backpressure: if a socket's buffered amount > 4 MB, drop `live` frames for it first, then disconnect with `bye: 'slow'`.

### 4.3 Parent channel (desktop app, W26)

When `pasabot-server` is spawned with a Node IPC channel (`stdio` includes `'ipc'`), it speaks a tiny message protocol to its parent only; nothing on the network can reach it. Without a channel (CLI, launchd, systemd, Docker) nothing changes.

| Direction       | Message                                                        | Meaning                                                                                     |
| --------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| server → parent | `{ type: 'pasabot:ready', url, sitesUrl, setupLink, stopped }` | listening; the real URLs (so port 0 works) and, with no owner yet, the first-run setup link |
| server → parent | `{ type: 'pasabot:state', stopped, since }`                    | reply to `pasabot:state`, and after every stop or resume                                    |
| server → parent | `{ type: 'pasabot:error', message }`                           | a stop request failed                                                                       |
| parent → server | `{ type: 'pasabot:state' }`                                    | ask for the global stop state                                                               |
| parent → server | `{ type: 'pasabot:stop-all' }`                                 | the global stop (W31) as `asSystem('desktop app')`; resume stays owner + re-auth on the web |
| parent → server | `{ type: 'pasabot:setup-link' }`                               | the app window needs a fresh first-run setup link (its page's code ran out or it came back) |
| server → parent | `{ type: 'pasabot:setup-link', setupLink }`                    | the link, or null once an owner exists; within 10 s of the last mint the same unused link   |
| (channel close) | the parent exited or was killed                                | the server shuts down cleanly: no orphan server                                             |

`pasabot:setup-link`, threat model: it is the only way besides the boot link and `pasabot setup-link` (both need the machine) to get a setup token, and it is reachable only by the process that spawned the server with the channel, never over HTTP/WS, so no web page, other origin or browser tab can ask for one. The launcher asks only when its shell says so (`{"cmd":"setup-link"}` on stdin) and answers on stdout (`{"event":"setup-link","url"}`); the macOS window says so when its claim page posts `need-setup-link` to the one script message handler it installs (`pasabotSetup`; accepted only from the main frame of the app's own origin, the sandboxed sites origin and every frame are refused) or when the window comes back (reopen, second launch, Open PasaBot). The page gets no token through the handler: the window moves the main frame to the new `#/setup?token=` link (same document, a hash change). Each mint replaces the older unused token (one live code), nothing is minted once an owner exists, and a mint within `SETUP_REMINT_MS` (10 s) of the last hands back the same unused link, so a reload loop writes nothing. Links are never logged on this path (server log, launcher, window log); the boot line in the server log is the only one, as before. When the launcher has no link (an owner exists, no server) the window tells its claim page with one data-less `pasabot:no-setup-link` DOM event, and the page says to reopen the app at once. A launcher attached to a server it did not start (`pasabot start`, status `external`) has no channel: it mints with the server's one-shot `mint-setup-link` entry on the same data dir (the DB-level mint `pasabot setup-link` does, same rules; it needs the data dir, so only that user on that machine can mint; the link only on its stdout). Shells without a window (the Windows tray, the Linux starter) open the browser, and while there is no owner every way they open the app asks for a fresh link at that moment (over the channel, or the minter for an external server) and opens that, never a bare or stale address: the boot link (for an external server, a minted one at first launch), Open (`{"cmd":"open"}`), Stop all on an external server, and a second launch. On Linux the starter's launcher (`--open-urls`) records `show: true` in the lock, so a second launch pokes it (SIGUSR2) and it opens the fresh link itself (inside the 10 s reuse); on Windows (no signals) the second launch mints. Once an owner exists they open the bare address. Links go to the OS opener as an argument array, never through a shell (`rundll32 url.dll,FileProtocolHandler` on Windows, ShellExecute with the URL as the file name in the tray, `xdg-open` then `gio open` on Linux), only plain http(s) addresses; a launcher that opens links itself hides the code (`token=<hidden>`) on its stdout, which the Linux starter appends to a log. Accepted risk: the opened link is an argument of the browser process. On Linux a browser that `xdg-open` starts keeps it in `/proc/<pid>/cmdline`, which other local users can read unless `/proc` has `hidepid`, and the loopback port is open to them, so on a machine shared with other accounts one of them could claim an unclaimed server with it inside 30 min. The boot link always had this exposure; every Open while unclaimed now repeats it (each mint replaces the older code). Windows hides other users' command lines from non-admins; macOS `open` hands the link over by Apple Events. A 0600 redirect file opened by `file://` path would keep the code out of argv, but confined browsers (Ubuntu's default snap Firefox, Flatpak) cannot read a file under the hidden `$PASABOT_HOME`, so the link would not open (apps/desktop/README.md). What still differs from the macOS window: no in-app window, so a claim tab left open past 30 min gets the refused-code line on submit, which says to click Open PasaBot in the PasaBot icon (a fresh link in a new tab), on Linux to start PasaBot again, or run `pasabot setup-link`; no HTTP route mints a code to renew it in place. A browser reaching the server (no handler) still asks for the code, with `pasabot setup-link` named in the hint.

Rules: adapters spawn the CLI with `execa` (no shell), cwd = workspace, env from `TurnInput.env` only, kill the whole process group on abort, and must emit exactly one `done`. A queue item whose payload carries `tools: 'none'` (added with W9: workflow model steps) runs with `TurnInput.tools = 'none'`, an empty `mcp` (no gateway URL or bearer) and no `nativeRef` (a fresh native session each time). It has no tools at all, the CLI's own included: the orchestrator answers every `permission` event of such a turn with `deny` (never tiered or auto-approved), and adapters switch the CLI's built-in tools off where the CLI allows it (claude: `--tools ''` and permission mode `default`; codex: read-only sandbox; opencode: deny all). Native sessions are scoped (`provider_sessions.scope` = tool mode `gateway`/`none`, the turn's effective trust, the sender's kind and trust, and for every sender but the owner its id (`id ?? name`) plus, for agent-to-agent work, the chain origin (`source.origin`)): a turn resumes only a session of its own scope and saving a session replaces only that scope's, so a tool-less step that read untrusted text is never continued by a tool turn (or the reverse), a stranger's, webhook's or lower-trust session is never continued with more authority, and two principals of the same kind and trust (two guests, two routines, two agents' delegations or one agent's for two origins) never continue each other's. Rows without a scope, or with the older kind-and-trust scope of a non-owner sender, are never resumed. `FakeProvider` replays a JSON script (`[{after: ms, event}]` plus `{expectPermission: {tool, decision}}` steps, which emit a `permission` event and assert the decision the server sends back) and is the reference implementation for the contract suite `runProviderContract(adapter)` in testkit.

Orchestrator hooks (W0 exposes via `providers.setPolicy()`; W3 installs its policy):

```ts
export interface ProviderPolicy {
  choose(
    agent: AgentDTO,
    lastError?: ProviderEvent & { type: 'error' },
  ): { providerId: ProviderId; model?: string; accountId?: string } | null;
  // session = the chat and session scope of the turn (per-session compaction bookkeeping)
  shouldCompact(
    agent: AgentDTO,
    usage: UsageSnapshot,
    session?: { chatId: string | null; scope: string },
  ): 'native' | 'reseed' | false;
  // for reseed / provider switch; `only` = the (redacted) messages the summary covers: the reseeded scope's own turns
  summarize(chatId: string, upto: string, only?: readonly MessageDTO[]): Promise<string>;
  account?(accountId: string): ProviderAccount | undefined; // resolves an accountId choose() returned (own CLI config dir)
  resumeAt?(agent: AgentDTO): number | undefined; // when usage-limited work with no fallback left may run again
}
```

How the orchestrator uses it: `choose(agent)` picks the provider for each turn (a server-set `providerOverride` wins); the chosen account goes into `TurnInput.account`, and its config dir (kept outside `$PASABOT_HOME`) is the one extra writable path of that run's sandbox. A turn that fails with `rate_limit`/`quota`/`auth` asks `choose(agent, lastError)` once; a different provider/model/account that is installed reruns the same item on it (one retry per item) and publishes `provider.switched` on `agent:<id>`. A `rate_limit`/`quota` with nothing left (or a retry that hits a limit too, which is booked with `choose(agent, lastError)`) is `held`, never failed: until `retryAfterMs`, else `resumeAt(agent)`, else 15 min. A `context_overflow` ends the session and reruns once. An `offline` error (the provider could not be reached at all, W34) asks `choose(agent, lastError)` only for an item whose payload carries `runEvenOffline: true` (routines marked "run even offline"): the policy answers the next reachable entry of the chain after the failed one without pausing anything, and the switch is published with `reason: 'offline'`; any other `offline` item is `held` like a usage limit (until `retryAfterMs`, else 15 min). A cloud CLI that lost the network reports `crash`/`timeout`; the orchestrator reads such an error as `offline` when its text carries a network-unreachable marker (`looksUnreachable` in core: ENOTFOUND, EAI_AGAIN, ECONNREFUSED, ETIMEDOUT, no route, `fetch failed`, `connection error`, ...) **and** the attempt had produced no text and no tool use yet; an `offline` error after text or tool use is read as `crash`, so an item is never rerun over side effects. After a finished turn whose `usage` reports `contextUsed`/`contextWindow`, it publishes `agent.context` and asks `shouldCompact(agent, usage, { chatId, scope })`: `native` calls `adapter.compact()` (falls back to reseed when the CLI has none or it throws); `reseed` ends the chat's native session for that scope (`end_reason = 'compacted'`); either way it publishes `provider.compacted`. Native sessions are kept per provider **and account** (`provider_sessions.provider_id` = `<provider>#<accountId>` when an account is used): a session is never resumed under another account's config dir. A finished turn ends the open sessions of the same chat and scope on every other provider/account (`end_reason = 'switched'`), so a provider that missed turns is never resumed. A turn with no native session to continue, in a chat that had one in the **same scope** (on another provider, or compacted), gets `TurnInput.seed`, built only from that scope's own turns (this agent's replies whose queue item has the same scope, plus the messages they answered): `summarize(chatId, replyId, older)` (the older ones, at most 200) + the last 10 of them (redacted; the turn's own text not repeated). Tool-less items never fall back, reseed or compact.

CLI lookup (`cliSearchPath(env)` / `findCli(bin, path)` in `@pasabot/core`): a server started by launchd, systemd or the desktop app has a bare PATH, so adapters detect and spawn their CLI on `cliSearchPath()`: the given PATH first, then the common install folders that exist, system and package-manager ones first (`/opt/homebrew/bin`, `/usr/local/bin`, the running Node's folder: npm CLIs start with `#!/usr/bin/env node`), then the per-user ones (`userCliDirs()`: `~/.local/bin`, `~/.npm-global/bin`, `~/.bun/bin`, `~/.opencode/bin`, `~/.volta/bin`, `~/bin`). The server runs what it finds there outside the sandbox (detect), so the host sandbox denies writes to every per-user CLI folder (Seatbelt `file-write*` deny; `writablePaths` refuses them, so bubblewrap never binds them read-write) and a file planted there cannot shadow a CLI installed in a system folder. `scrubbedEnv()` hands the CLI that same PATH.

Brain API keys (`ProviderAdapter.keyEnv?: readonly string[]`, e.g. Grok's `['XAI_API_KEY']`): the runner reads each named entry from the vault (the agent's own `agent:<id>` scope first, then `global`) and passes it in the turn's env as `scrubbedEnv({ NAME: value })`, for agent turns and the brain test alike; nothing else from the vault and nothing from the server's own env reaches the CLI. Detection never reads a value: `withVaultKeys(status, adapter, await vaultKeyNames(vault))` (`@pasabot/core`) turns an installed brain whose key name is a `global` vault entry into `signedIn: true` (`GET /api/v1/providers` and the Brains page); an ACP adapter's own `signedIn` check sees only the env the CLI will get (the scrubbed allowlist plus its own `env`), and a key variable set only in the server's env reads as `'unknown'`.

Brain test (`ProviderRegistry.probe?(id, { prompt, model?, account?, timeoutMs })`, set by the host from `Orchestrator.probe`): one tool-less turn (`tools: 'none'`, empty `mcp`) with no agent, chat, run row, queue item or native session, through the provider's own adapter in the runner sandbox, with `scrubbedEnv()` and a throwaway workspace `$PASABOT_HOME/workspaces/.brain-test-<id>` removed afterwards. Every `permission` event is denied, the turn is aborted after `timeoutMs`, and it answers `{ ok: true, reply, ms, model? }` or `{ ok: false, kind: ProviderErrorKind | 'not_installed', message, ms }` with every text redacted (7.3). Only the provider-ops Brains page calls it (owner only, 6 per minute, 60 s, never stored).

W3 policy rules: on a fallback, retry the primary after the reported reset (usage check every 15 min); work blocked by a usage limit with no fallback is `held` until `resume_at`, not failed; compaction threshold is per agent (`limits.context_pct_compact`, or absolute tokens); two compactions in a row that free < 10 % of the window stop compaction and notify instead of looping.

Binding rules: each place maps to one PasaBot chat and an orchestrator agent; `allowed_senders` empty = only the owner's linked identity; others are dropped (and audited). Adapter rules and shared helpers (added with W4): `InboundMessage.externalId` is unique per binding across places (Telegram uses `<chatId>:<messageId>`); a DM always has `mentionsBot: true`; `sender.externalId` is the immutable platform id; `RemoteFile.url` never embeds a credential. `@pasabot/core` exports the binding rules as pure functions (`channel-policy.ts`): `decideChannelInbound` (order: a link command posted outside a DM is `burn_link` — the runtime invalidates that code and writes a `channel.link_code_exposed` audit record, and the text never becomes a turn → other bots ignored → `/link CODE` or `/start CODE` honoured only in a DM → group message without a mention ignored → stranger dropped with an `channel.sender_dropped` audit record → empty ignored → enqueue with `channelIdemKey` and a `SenderInfo` whose trust is `channelOwnerTrust` for the owner, one level lower for allowed senders), `channelMayAnswerApproval` (owner only, tier < 3), `newChannelLinkCode` / `hashChannelLinkCode` / `parseChannelLinkCode` / `findChannelLinkCode`. `edit` to a text longer than the platform limit puts the first part in the edited message and posts the rest as follow-ups; nothing is cut. `@pasabot/testkit` exports `runChannelContract(name, setup)` (each adapter supplies a mocked platform: owner, stranger, a display-name impostor and another bot; a DM, a stranger DM and a group; plus its `textLimit` and `botTexts(place)`) and the reference `FakeChannel`.

Additions with W5 (Slack, WhatsApp): `ChannelContext.state?: ChannelStateStore` (`load()`/`save(value)`, `save('')` clears) is opaque per-binding adapter state kept in the vault (`vaultChannelState(vault, bindingId, actor)` in `@pasabot/core`, one entry `binding:<id>:state` in scope `module:channels`); the binding runtime passes it to `connect`. The channels module passes `pairing` a staging store (`vaultPairingState`, entry `binding:<id>:pairing`, cleared when a pairing starts, is aborted, expires or fails) and on `done` moves it into the live entry with `promotePairingState`, so an unfinished pairing never touches a working session; a pairing is refused with 409 `already_linked` unless the binding is unlinked (`auth_failed`) or disabled, and Settings → Channels offers linking only for an unlinked binding (not while a linked one reconnects). `ChannelAdapter.options` names non-secret settings the owner may set (kept in `channels_binding.config`, e.g. WhatsApp `ownNumber`); `ChannelAdapter.inboundHttp` + `ChannelConnection.handleHttp(req)` take push events: the channels module mounts `POST /hooks/channels/<bindingId>/events` (rate-limited, 1 MB) and hands the raw request to the live connection through `ChannelRegistry.deliverHttp` (set by the runtime); the adapter checks the platform signature itself. Pairing (`POST|GET|DELETE /api/m/channels/bindings/:id/pairing`, owner session): starting one requires `{ acknowledgeRisk: true }` (the web shows the terms-of-service / ban-risk notice first) and is audited (`channel.pairing_started`, `channel.paired`); the QR code is rendered on the server as an SVG data URL and polled by Settings → Channels; on `done` the binding restarts with the stored session. A pairing adapter has no secret fields; the contract harness then supplies `state` / `badState` stores instead.

Addition with W25 fixes: `ChannelContext.audit?(action, data)` lets an adapter leave the owner a note about something that never became a message (e.g. board messages it had to skip). The binding runtime writes it to `audit_log` as `channel.<action>` (target = the binding id) with `data` redacted and capped at 4000 characters; an `action` outside `[a-z0-9_.]{1,60}` is refused and logged. Optional: hosts without an audit trail leave it unset.

### 5.3 Triggers

```ts
export interface TriggerSource<Spec = unknown> {
  readonly kind: 'manual' | 'schedule' | 'webhook' | 'event' | 'github' | (string & {});
  readonly specSchema: ZodType<Spec>;
  arm(id: string, spec: Spec, fire: (f: TriggerFire) => Promise<void>): Disarm;
  test?(spec: Spec): Promise<TriggerFire>; // dry-run for "test routine"
}
export interface TriggerFire {
  routineId: string;
  at: number;
  source: string;
  payload: unknown;
  idemKey: string;
}
type Disarm = () => Promise<void>;
// schedule: { cron: string; tz: string }   webhook: { secretRef: string }   github: { installId: string; events: string[] }
// event:    { topic: string; type: keyof EventMap; filter?: JsonLogic }
```

Missed schedules while down: fire once on boot if `catchUp: true`, else skip and log. The scheduler re-reads the routine (enabled? still exists? same trigger?) just before firing, and writes the `routines_fire` row before advancing the schedule. Schedules are also exported as a 30-day iCalendar feed (session auth).

**Fires are data.** A fire's payload is appended to the prompt as quoted, labelled data; it can never grant tools, change trust or skip approvals. Every fire runs at `min(created_trust, agent trust, sender trust)`; webhook, GitHub and event fires count as non-owner senders.

**Webhook contract** (`POST /hooks/routines/<path_token>`): headers `X-PasaBot-Timestamp`, `X-PasaBot-Delivery` (sender-chosen unique id), `X-PasaBot-Signature: v1=<hex HMAC-SHA256 over "v1:{ts}:{deliveryId}:{body}">`, constant-time compare, ±5 min window. Delivery ids persist via `queue_items.idem_key = webhook:<routineId>:<deliveryId>` (≥ 7 days, survives restarts). Responses: `202` accepted (a duplicate also gets `202`, nothing re-runs), `401` bad/missing signature or stale timestamp, `413` body > 64 KiB, `429` + `Retry-After` per-route rate limit, `503` routine paused or agent queue full. At most 64 webhook routines per host. No bearer mode.

**Routine targets:** `chat` runs in the agent's own chat; `thread` opens a separate thread with a fresh provider session seeded with a handoff of recent messages. A reply that is exactly the silent marker (`(quiet)`; our own convention) stores the fire as `silent` and sends no notification, so a "nothing new" run stays quiet.

## 6. Message queue semantics (crash-safe FIFO per agent)

- **One runner per agent.** Items for an agent run in `(priority, seq)` order, so a new chat request runs ahead of queued routine/workflow runs and FIFO holds within each priority; a global pool caps concurrent agents (`maxConcurrentAgents`, default 3); per-agent queue depth cap (default 50) → enqueue refused with 503.
- **Enqueue** = one `INSERT` in a `BEGIN IMMEDIATE` transaction; `seq = max(seq)+1` for that agent; `idem_key` UNIQUE makes redelivery a no-op.
- **States:** `queued → leased → running → done | failed | cancelled | interrupted`, plus `held` (usage limit, no fallback; requeued at `resume_at`).
- **Lease:** the dispatcher takes the head item only if no item for that agent is `leased|running`, sets `lease_owner = <bootId>`, `lease_until = now+30 s`, renews every 10 s while running.
- **Crash recovery (boot):** any `leased` item → back to `queued` (nothing ran). Any `running` item with an expired lease, or a lease held by an earlier boot (one server owns a `$PASABOT_HOME`, so that process is gone) → `interrupted` (it may have had side effects), never retried automatically; the chat gets a system message "interrupted, Retry / Skip". For `message`/`task`/`handoff` items the agent's queue is **blocked behind it** until the owner picks, which preserves conversational order. `routine`/`workflow` items never block: they are marked `interrupted`, the owner is notified, and the queue continues (so an overnight routine crash cannot stall chat). A `QueueKindSpec.admit(item)` hook, when set, runs at dispatch time right before an item of that kind executes (after any requeue, retry or hold too): a returned reason (or a throw) ends the item `cancelled` with that reason and it never runs; W21 uses it to refuse an `automation.run` whose token was revoked or expired, or whose agent's automation switch is off, while it waited. After the kind's `admit`, every **queue gate** (`QueueService.addGate(gate)`, any module, every kind) is asked the same way: `null` runs the item, `{ refuse }` ends it `cancelled` without a run, `{ hold: { until, reason } }` parks it `held` (released at `until`, or earlier with `hold(id, now)`), and a throwing gate holds it for a minute (fail closed). W32 budget caps use it. Every dispatch-time refusal (admit or gate) publishes `queue.refused { itemId, agentId, chatId, kind, reason, workflowRunId? }` on `agent:<id>` (`workflowRunId` from the item's source when it is a workflow step); the routines module records such a fire, or the fire that started that workflow run, as `skipped` with the reason. Only kinds whose `QueueKindSpec` sets `idempotent: true` (core: `routine`; a `blocksOnInterrupt` kind can never be idempotent, `registerKind` refuses it) requeue up to 3 attempts instead, and only when the item's payload also says `retryOnCrash: true`; `message`/`task`/`handoff` never auto-retry whatever the payload says. Recovery also closes the crashed turn's `runs` row as `interrupted` (`finished_at` set, `run.finished` published) and revokes its `run_tokens` in the same transaction. A **graceful shutdown** (SIGINT/SIGTERM, `close()`) is not a cancel: running items are aborted with a shutdown reason and left `running`, so the next boot recovers them exactly like a crash (`interrupted`, Retry/Skip). While up, the dispatcher also sweeps expired leases (items it is not running, e.g. after a failed state write) through the same recovery.
- **Pause/resume** per agent (`agent_queue_state.paused`): stops leasing; the running item finishes. **Cancel** a queued item = `cancelled`; cancel running = abort signal → adapter kills the process group → `cancelled`.
- **Reorder/edit** only while `queued`. **Steer (default)**: a new message in the chat of the running turn is passed to `adapter.steer()`; if the adapter lacks it or returns false, the owner switched the chat to "queue", or the message has attachments (steering passes text only; files are copied into the workspace per run), it is enqueued at chat priority. A turn that has already given its final message (`text.final` or `done`) is not steered any more: the message is enqueued for a turn of its own. An adapter's `steer()` returns true only for text the running turn will still answer (the FakeProvider answers each steered text before its one `done`). The turn's reply message keeps every `text.final` of the turn, joined by a blank line, so a steered answer is added to the reply it joined, never written over it. The orchestrator keeps each steered message (text, sender, message id) on the running turn: when the turn ends `done` they were answered; when it ends any other way (failed, cancelled, interrupted, or failed and retried on a fallback provider) each one is enqueued again as a `message` item of its own with its original sender, replying to its message, so a steered message is never taken and dropped (a steered text the turn had already answered before it failed is answered once more). "Interrupt and send now" = cancel running + enqueue at priority 0.
- **Provider errors:** `rate_limit|quota` → ask `ProviderPolicy.choose()` for a fallback and retry the same item once on it (attempts+1); no fallback → `held` until the reported reset; `auth` with no fallback → `failed` with the error shown. Finish/error of a run notifies the owner via `Notifier` (silent routine fires excepted). `context_overflow` → compact/reseed then retry once.
- **Report back (collab, ws/threads).** A delegation is a task in a batch (the asking run). Once that run ended and every task of the batch is final (or the report wait, default 10 min, ran out: then what came back is told with who is still working, and each late answer follows), the asker is woken ONCE with a `task` item in the chat where it was asked (`replyTo` the message it answered), as the answering helper at the lowest task trust, its text labelling the answers as other helpers' words. Its reply gets a `collab.report` block (who answered, each full answer, the files and pages they made); a calm `collab.status` line shows meanwhile. A report turn that fails, is cancelled, never runs or says nothing → the server posts the report itself (`mode: fallback`), so an answer is never lost. A task whose own run delegated finishes with that run's report (nested work reports up). Wakes are idempotent (idem key per batch + task states, tasks marked in the same transaction; every open batch is checked again at start). Caps: 3 hops, 8 tasks per chain (everything one person's message started), then a plain line.
- **Durability:** `synchronous=NORMAL` in WAL; queue writes are tiny; a periodic maintenance pass (default every 10 min) prunes the `events` ring and runs `wal_checkpoint(TRUNCATE)` when no item is running.

### 7.1 Approval tiers

| Tier | Meaning                             | Examples                                                                                                                                                      | guarded | standard                               | trusted (default for new agents)                       |
| ---- | ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------- | -------------------------------------- | ------------------------------------------------------ |
| 0    | Read inside PasaBot                 | memory search, list tables, read chat history                                                                                                                 | auto    | auto                                   | auto                                                   |
| 1    | Change inside the agent's own space | write workspace files, own datastore tables, remember                                                                                                         | auto    | auto                                   | auto                                                   |
| 2    | Visible or outbound effect          | post to an outside channel, message another agent's external place, http to a non-allowlisted host, install skill/MCP, publish site, start background process | ask     | auto for allowlisted targets, else ask | auto                                                   |
| 3    | Dangerous                           | read a secret value, computer use, browser on logged-in profiles, delete data, drop shared tables, shell outside workspace                                    | ask     | ask                                    | ask unless owner set per-tool "always allow" (audited) |

- Ask = an `approvals` row + an approval card in the chat + push notification; expiry default 30 min → `expired` = denied. A workflow's approval step is a detached approval (no chat card): it shows in a decision bar pinned above every screen and in the "needs you" count, waits up to 7 days, and survives a restart.
- **Default level (owner decision 2026-11-13, matching the reference product):** a new agent starts at `trusted` unless the create request names a level or the owner set a stricter server default (`settings` key `agents.defaultTrust`, `GET`/`PUT /api/v1/settings/agent-trust`, owner session only). Creating the agent is the owner's one consent to it; tier 2 then runs without asking on the owner's own turns. `standard` and `guarded` stay selectable per agent and as the server default. First-run setup, the agent form (while `trusted` is chosen) and Settings show one plain paragraph saying what `trusted` lets the agent do and how to make it stricter (en + fil). Existing agents keep their level. These hard rules hold at every level and are never relaxed by the default: channel-originated turns are capped at `standard` (5.2); tier 3 always asks and is answerable only from a paired device with re-auth, never from a channel; `created_trust` never escalates (7.4); non-owner senders never inherit the owner's trust and never auto-approve tier 2+.
- Turns started by **non-owner senders** (channel strangers, webhooks, other agents acting for them) run one trust level lower and never auto-approve tier 2+.
- Creating or editing a routine, workflow, webhook, MCP server or skill is tier 2; deleting a routine or workflow is tier 3 (always asks, at every trust level). Renaming an MCP server, or giving it a new command/URL, is tier 3: its name is what always-ask cards show.
- A tool registered with `noAlwaysAllow: true` (`ToolDef`, e.g. the `computer_*` action tools, which can click the owner's own approval UI on macOS) is never covered by a per-tool "always allow": setting one for it is refused and the gateway asks every time, at every tier and trust level (the server's `autoApproves`, the one place an action may skip the ask, takes the `ToolDef` and returns false for it). Module code may not call such a tool directly: `ModuleHost.tools.invoke` rejects it, so it runs only through the `/mcp` gateway, which asks.
- **Always asks (action classes).** `ToolDef.actionClass` names what a call does: `money` (buy, pay, check out, order, subscribe, enter or use payment details, send money or crypto), `outbound-message` (an email, chat, DM or post to anyone other than the owner's own linked chats; the agent's reply in the owner's own bound channel is not a tool call and is not gated), `delete`, `publish`. The `/mcp` gateway asks for every call whose class is `money`, `outbound-message` or `delete` (`FIXED_ALWAYS_ASK` in `@pasabot/protocol`; `delete` since W38, see below), or a class the owner added (`settings` key `approvals.alwaysAsk`, owner-only `GET`/`PUT /api/v1/settings/always-ask`; the owner may add `publish`, never remove the fixed three), at every trust level including `trusted`, whatever the tool's own tier, and these never take a per-tool "always allow" (same rule as `noAlwaysAllow`).
  - Where the class comes from: core and module tools declare it; a connector manifest's `toolClasses` (GitHub: issue/PR/comment posts); for any other outside MCP tool the `mcp` module runs a conservative, regex-free default classifier (`classifyToolText` in `@pasabot/core`: tool name and description words; names starting with a read verb such as get/list/search are never classed) when the tool list is fetched, stores the result (`mcp_server.tool_classes`), and the owner corrects it per tool on the MCP page (`PUT /api/m/mcp/servers/:id/classes` → `class_overrides`, which win over `declared_classes` and the default). A class is never re-derived from agent text at call time; an agent argument may only add one (the browser and computer `intent`).
  - Fails closed: `tools_invoke` lists (and classes) a server's tools before checking a call whose tool is not in the stored list; when the list cannot be fetched, or the server does not list the tool, the call is refused, never run at the normal tier. Servers from before tool classes existed have their cached list dropped once (migration `202611141700_tool_classes_backfill`). Connector servers get their manifest's `toolClasses` again at every boot: the `mcp` module publishes `mcp.ready` on `module:mcp` at the end of its registration, and the `connectors` module answers with one `connectors.mcp` event per ready install marked `classesOnly` (only `declared_classes` changes; nothing is created and no owner setting is touched).
  - Browser and computer: the managed browser reads the page in the renderer (the top document, the field attributes of child frames such as an embedded card form, and the element the action targets), and a deterministic detector recognises a checkout/payment page or a compose/send form. Money: cc-* autocomplete or card/cvc/iban fields anywhere, an address word such as checkout/payment/pay/billing/purchase/buy/subscribe (a cart or order-history address alone is not enough), or a short target label such as "Buy now", "Pay", "Place your order", "Start subscription". A message: recipients (to/cc/bcc) plus a body in the target's own form, a body on a compose/send/message address, or a short target label such as "Send" or "Post". A `browser_click`/`browser_type` there asks; one whose `intent` argument did not declare it is held and asked with a warning on the card; a page that is both gets a money card with the message facts too. Browser actions run one at a time per profile, and right before the click or entry the page is read again under that lock: an address or class other than the one checked and approved, a card that would now say anything else (`askBasis`: the recipients, subject and body of a message, or the merchant, total, card number and message facts of a money action, as captured when the card was built; the page's own script, autocomplete or a parallel call may change them while the card waits), or a target that is not on the page now, refuses the action; the action then runs on a handle to that very element, never on a page that loads later. The computer driver sees pixels only: its actions are tier 3 and always ask anyway, and a declared `intent` gives the card its class.
  - The card (`ApprovalDTO.ask` = `{ class, fields, undeclared? }`, column `approvals.ask`) is built by the server from the call's arguments or the captured page (`askFromArgs`, or the tool's `actionDetails`), never from the agent's own summary: money shows item(s), merchant, total with currency and a payment-method label (`maskPaymentLabel`: any 12+ digit run, whatever non-letter characters separate the digits, becomes `•••• 1234`, never the number); a message shows recipients, channel, subject and the full text; a field the call does not give reads "not stated". These facts are a summary: every always-ask card ends with the tool (`tool`) and its full arguments (`arguments`, compact JSON), so a destination the summary does not map (`channel_id`, `owner`/`repo`/`issue_number`) is still shown. A value the server knows (an MCP server's channel: its name plus its fixed id and URL host or command) is shown beside an argument-given one, never instead of it. An outside MCP call that passes arguments its tool's input schema does not list is refused on an always-ask class (a decoy `text` beside the real `body`). Values pass the secret redaction; for money, payment card numbers are also masked in the stored and served `action` and on the card (`maskCardNumbersDeep`): by key (`card`, `cardNumber`, `pan`, or `number` inside a payment object, shown as a label and its last 4; a `cvc`/`cvv`/PIN as `•••`), and anywhere else a Luhn-valid 13-19 digit run, whatever separates the digits. The arguments JSON is masked by key once, never again as text, where an amount could pass for a card. A message card keeps its digits: a phone number is the recipient.
  - Answering: money approvals are tier 3 (password/passkey re-auth on approve). Every always-ask approval is approvable only through the owner-session REST route: `ApprovalService.decide` (modules, automation, linked machines) and channel replies refuse to approve one (a channel may still deny). It shows in the chat, in the pinned decision bar (Review opens the full card) and in the "needs you" count, and expires like any approval.
  - Refusals: a deny or expiry reaches the agent as `refused: …, do not try it again`. The same call (tool + arguments fingerprint, `action.fp`) in the same run is then refused without a new card, and after 3 refusals of a class in a run, or 5 for one agent within 10 minutes, further calls of that class are refused without asking.
  - **Known limit, stated plainly (owner decision 2026-11-14): an agent you give a terminal can do anything a terminal can; the always-ask cards cover tools PasaBot can see.** Shell-capable tools (the provider CLI's own `Bash`-like command execution, and raw web fetch/HTTP tools such as `WebFetch`) can send a message or pay without going through a classified tool: a shell `curl` that sends mail or charges a card, or an `osascript` that sends a message, has no class PasaBot could derive from the command, and a CLI without a permission bridge is outside the gateway altogether (7.2 sandbox only). The permissive default stays: these tools are tier 2 and auto-approve for a `trusted` agent on an owner turn. What the owner gets instead is a **per-agent toggle "Ask before terminal and raw web commands"** (`agents.ask_shell_web`, `AgentDTO.askShellWeb`; `null` = the trust level's default: **off at `trusted`, on at `standard` and `guarded`**; owner session only via `PATCH /api/v1/agents/:id`, never an agent, channel or automation). When it is on, every permission-bridge call of a terminal or raw web tool (`isShellOrRawWebTool`: `Bash`, `BashOutput`, `shell`, `exec_command`, `run_shell_command`, `WebFetch`, `web_fetch`, … by normalised name; never a gateway `mcp__` tool, which the gateway classes itself) asks, through `cliToolAutoApproves` in the gateway; turning it off never makes a tier 3 call or a non-owner turn auto-approve. Settings → "Always asks" says this limit in the same words, and the agent form carries the toggle (en + fil). No core tool messages other people today.
  - **Third fixed class (W38, built): deletes outside the agent's own workspace.** The delete card (`ACTION_CLASS_FIELDS.delete`) shows `target` (what: paths, table, resource), `where` (another agent, shared, outside the workspace, which server or connector), `count` (how many, when known), then the tool and its full arguments; a fact the call does not give reads "not stated". A tool whose delete may stay inside the workspace returns the class per call (`ToolDef.actionClass` as a function), never statically. Any tool call that deletes data outside the calling agent's workspace always asks, at every trust level, with no per-tool "always allow" and approval only in the app, like money and outbound messages. The sites: file tools whose resolved target (walked physically: each existing symlink followed before the next `..`; unresolvable counts as outside) is outside `<workspace>`, an ACP agent's `kind: 'delete'` included (its `move` when a location is outside); a terminal delete command (`rm`, `rmdir`, `find … -delete`, `git clean`, …, read by a linear tokenizer, command names case-blind) with a target outside the workspace or unresolvable, only while the agent's "Ask before terminal and raw web commands" toggle is on (with it off, the terminal limit below stands). In a command line a target is unresolvable when a component before its last does not exist yet, or when the line makes links (`ln`, `cp -s`, `mount`); so is anything handed to a shell without `-c` (`… | sh`, a script), `eval`/`source`, `env -S` (re-read), a git alias, command-valued `-c` or non-built-in subcommand, a shell or interpreter after `-exec`/`xargs`, and input typed into a running process (`write_stdin`). `mv`, `rsync --delete`/`--remove-source-files`, and `cp`/`install`/`ln -f`/`rsync` onto a path are deletes of their outside operands. An ACP `execute` call is a terminal tool (`acp.execute`, `acp.fetch` follow the toggle too), and the orchestrator's permission path refuses a repeated refused delete like the `/mcp` bridge; outside MCP and connector tools tagged destructive (`destructiveHint: true`, a manifest `destructive` tag, or an owner tag; only the owner removes a tag); and in the datastore, dropping, truncating, or deleting or replacing rows of a table the agent did not create. Before W38 `delete` was an owner-optional extra class; deletes inside the agent's own workspace keep their normal tier. The class lives in `packages/core` (`action-class.ts`); the gateway rule, the permission bridge and the tool sites are W38's (ROADMAP). Owner-added `delete` in `approvals.alwaysAsk` from before W38 is harmless (the class is fixed now).
  - **Declined:** bank-portal helpers and automated OTP handling. An agent never drives a bank login and never reads or enters one-time passwords; logins and OTPs stay with the owner, money stays behind the money card.
- The provider CLI's own tools (shell, file edit) are governed by: (a) the permission bridge when `caps.permissionBridge` is true (routed to the same approval flow, tier by tool category), (b) CLI-native permission modes chosen per trust level, (c) the runner sandbox below. We say plainly in the UI that a "trusted" agent with a CLI that has its own shell can do anything the runner user can.

### 7.4 Trust propagation (agents may narrow, only the owner widens)

- Every effective trust is `min(...)` of the chain that caused it: sender, agent, and for anything created by an agent the `created_trust` recorded on the routine, workflow, MCP server, skill or token. A run of an agent-made workflow acts as its maker and is also capped at that maker's trust as it is now (a demoted or removed maker lowers every later run), whoever starts it, an owner's routine included. Automation turns run at the token's `trust` (max `standard`) and never auto-approve tier 3.
- Agents (via `/mcp` tools) may only narrow access: lower their own trust, shrink allowlists, revoke grants, disable things. Widening (trust level, allowlists, per-tool "always allow", `mcp_agent.level`, automation tokens, `channels_sender.trust`) is REST-only under an owner session.
- The default for new agents (`trusted`, 7.1) is the owner's choice through owner-only REST; no agent, channel, webhook or automation turn can create an agent or change `agents.defaultTrust`.
- `mcp_agent.level`: `none` (hidden), `use` (call tools), `manage` (edit config, still tier 2), per agent and optionally per role. A role row matches the turn's effective trust (`effectiveTrust(agentTrust, sender)` in `@pasabot/core`, the same rule approvals use), not the agent's static trust; on a turn below the agent's own trust an agent row can only lower what that role gets.
- Injection suite (W27, seeded by each owner W): a stranger-, webhook- and agent-started turn each try to create a routine/workflow/MCP server that later fires with more trust than its creator, widen a grant through `/mcp`, and delete a workflow without asking; all must fail.

### 7.3 Secrets vault

- Encryption: XChaCha20-Poly1305 (libsodium) per secret; data key wrapped by a master key from the OS keychain (macOS Keychain / libsecret) or `vault.key` (0600) or a passphrase (argon2id) in headless mode. `rotateKey()` re-wraps. Keychain failures fail closed: only a certainly missing item (exit 44) creates a key, never with `-U`, and only a key that reads back is used; anything else (locked, prompt refused) makes the vault unavailable for that run and leaves the stored key alone, so a locked keychain at boot can neither lose the saved secrets nor overwrite the real master key (2.3).
- Agents get **references** (`{{secret:name}}`), resolved server-side when a tool/connector/MCP process starts (env injection) or a request is made. Raw value reads are tier 3. A reference granted to an agent is an entry in scope `agent:<id>`; tool handlers resolve it through `ToolCtx.vault` (`agentScopedVault`: the run's own agent scope only, every read audited). Agents ask for a missing key with the vault module's request tool; the owner fills it from Settings → Vault (W14). `tools_invoke` arguments may carry `{{secret:NAME}}` inside any string: the gateway fills it in from the agent's own scope only (a name that is not granted, unknown or malformed fails closed before the outside tool is called), approvals and events keep showing the placeholder, and the filled values (and their encoded forms) are redacted out of the result and any error.
- **Redaction**: every outbound text (messages, channel sends, logs, run_events, diagnostics) passes a filter that replaces any known secret value (and common token shapes) with `[secret:name]`. Since W14 the filter also matches each value's JSON-escaped, URL-encoded, base64 and base64url forms, and a backend (Bitwarden/1Password) value joins the set the first time it is fetched. A reply that is still streaming passes `Redact.stream`, which also holds back a tail that could be the first part of a known value, so a secret split across deltas never shows any part of it, however long (no cap on the hold; live deltas and the partial body saved while streaming). It also holds back an unterminated token shape at the tail (an open `-----BEGIN … PRIVATE KEY-----` block, a trailing `sk-`/`gh[pousr]_`/`xox[abprs]-`/`AKIA` run, a Telegram `<digits>:` token still short of its 35 chars), found with a linear scan. Saving a value over a backend reference makes the entry `local` again (the reference is dropped), and the reverse.
- Backends: local (default), Bitwarden CLI, 1Password CLI as read-only reference backends.

### 8.1 Computer use on a Mac: PasaBot Screen Helper (W16, W34)

**Why a separate helper.** macOS grants Screen Recording and Accessibility to the _responsible_ process. Agent CLIs
run as children of the server (under `sandbox-exec`), so a grant to the server (or the Terminal/node that runs it)
is every agent's grant: an agent could run `screencapture` or its own binary from its workspace as an ordinary
tier 1/2 command, with no approval and no log, and PasaBot could not take the grant back. So the server never holds
them. **PasaBot Screen Helper** (`apps/desktop/macos/ScreenHelper.swift`, bundle id `ai.pasabot.screenhelper`,
inside `PasaBot.app/Contents/Helpers`) is the only process that does; the desktop launcher starts it through
LaunchServices (`open -g -a`), never as its own child, so it is its own responsible process.

**Channel.** A unix socket `$PASABOT_HOME/run/screen.sock` (created 0600 under umask 0177, in a 0700 folder; no TCP
port). The helper accepts a peer only if `getpeereid` says it is the same user, then sends a random nonce; the peer
must answer HMAC-SHA256(key, `hello|<nonce>`) or is cut off. The key is 32 random bytes the launcher writes fresh to
`$PASABOT_HOME/run/screen.key` (0600) on every start (the agent sandbox denies `$PASABOT_HOME`); it never crosses the
socket, both ends refuse a key, socket or folder with group/other bits, and the helper quits when the key is removed
(PasaBot stopped) and reloads it when it changes.

**Grant protocol.** Every verb that sees or touches the screen (`screenshot`, `displays`, `move`, `click`, `type`,
`key`, and `resume`) needs `{ id, exp, mac }` with `mac` = HMAC-SHA256(key, `grant|<id>|<exp>|<verb>|<args>`), where
`<args>` is the exact coordinates/button/keys or the SHA-256 of the typed text. The server mints one (`GrantIssuer`)
only on a path the owner approved: a tier-3 tool handler (the gateway runs it only after the owner approved that
card with re-auth), the owner's own take-over, live view and "Try it" (owner session). Grants live 30 s and are
single use; the helper refuses, in this order: an unknown verb, a missing/forged/mismatched grant, an expired one,
one more than 60 s ahead, a replayed id, then a stop, missing permissions, the rate (8 inputs or 6 pictures per
2 s), typing while a password box has the keyboard (secure event input or a focused `AXSecureTextField`), and any
input aimed at a protected window (System Settings, SecurityAgent and other password/keychain/permission prompts,
Keychain Access, its own windows). Grant-free verbs only report or reduce: `status`, `stop`, `open_settings` (two
fixed panes; it only opens them, the owner flips the switch). The TypeScript reference (`helper/guard.ts`) and the
Swift guard share a test vector.

**Stops.** Holding Esc for one second, or the helper's menu, cuts control at once: the helper latches `stopped` and
tells the server, which turns every agent's macOS switch off and closes the display; Stop all (W31) sends `stop` and
closes the display. Only an owner action (turning an agent on with re-auth, resuming Stop all with re-auth) sends a
granted `resume`. While it acts the helper shows a menu-bar dot and an orange screen border (excluded from its own
screenshots).

**What it still cannot stop.** The helper drives the owner's real screen, so an approved click can land on anything
not listed above; that is why every action is a tier-3 card with a picture of where it lands. An agent that can
call LaunchServices could start a second copy of the helper with its own home; the helper refuses a second
instance (`LSMultipleInstancesProhibited` plus a running-copy check), but with an ad-hoc signature it cannot verify
who launched it. With a real signing identity (`SCREEN_HELPER_SIGN_IDENTITY`) the next step is a code-signing
requirement on the peer. Ad-hoc builds also lose the macOS permissions on every rebuild (the owner grants them
again).

**Screen helpers vs approvals (security review 2026-11-15).** The threat: two parallel tool calls, A =
`computer_click` at the spot where card B's Approve button sits in the owner's PasaBot window, B = a tier-3 money,
delete or typing action. Approving A once must never also approve B. The helper refuses PasaBot's own windows when it
can read window titles; the server does not rely on that and enforces, in the core approvals code
(`apps/server/src/approvals`, the `/mcp` gateway and `auth`):

- **Fresh re-auth per computer-use card.** A tool with `ToolDef.screenControl` (every `computer_*` action tool) files
  its approval with `screen = 1`. Approving it needs a re-auth made for that one card (`POST /api/v1/auth/reauth`
  with `for: <approval id>`, password or user-verified passkey, at most 2 min old, used once); the 5-minute window
  never counts, and a re-auth made for one card opens no window for anything else. A screen card is answered only
  in the owner's app (`deviceOnly`), never by a channel or module. The re-auth field is a real password input
  (`type="password"`, e2e-asserted), and the helper refuses to type into secure input, so it cannot fake the re-auth.
- **One at a time, and quiet while the screen moves.** An agent has at most one screen card pending (the gateway
  refuses a parallel second call with no card, and `request` refuses it again in the same tick). While any agent's
  screen action runs, and for 2 s after (`SCREEN_QUIET_MS`), the server refuses every approve of any kind: REST
  answers 409 `screen_busy` and the card says "Wait a moment — a helper just used the screen"; a channel or module
  yes is refused too. Deny always works (refusing is safe). The app never retries on its own.
- **Sensitive cards while a helper is active.** Each grant to move, click, type or press keys calls
  `ApprovalService.noteScreenGrant()`; for the next 30 s (`SCREEN_ACTIVE_MS`) every tier-3 or always-ask card (money,
  deletes, messages to other people, the vault, trust and permission changes) needs a fresh re-auth for that card,
  whatever the 5-minute window says.
- **Card nonce.** Every approval row carries a random `nonce`, in what the owner's app renders (owner topics, the
  chat card, `GET /api/v1/approvals`) and never in what modules read through their port. `POST …/approve` must send
  `{ nonce }` matching that card (403 `wrong_card` otherwise), so one card's answer never approves another; a replay
  of a decided card is 409 `not_pending`. The fresh re-auth is bound to the session and the card.

Still open: the nonce is per card, not per session (any owner session that renders the card can send it); owner
REST settings that widen access (an agent's trust, the macOS switch) keep the 5-minute re-auth window rather than a
per-action one; and a helper that could type into a browser's developer console could schedule a request after the
2 s window (the helper's own-window refusal and the per-card re-auth for every sensitive card are the defences).

### 8.2 Cards are not approvals; cards are the owner's (W40, r7)

- A card (`core.card`, `CardService`) may open a flow (an `href` inside the app), settle itself, or run its own
  source's server handler (Try again, Remind me, Undo, Take over). It never approves anything: no card action reaches
  `POST /api/v1/approvals/:id/approve`, a module's `ApprovalService.decide` refuses to approve a tier-3, always-ask or
  screen card, and the first-run "needs your OK" cards only open guided pages (this computer opens the computer
  module's own setup card for the main helper, `#/computer?agent=<id>`, whose "yes" needs the owner's password).
- Reads are the owner's: `CardService.open(viewer)` and `detail(id, viewer)` take the viewer and give a member or a
  guest nothing; `GET /api/v1/cards`, `GET /api/v1/cards/:id/detail` and `POST /api/v1/cards/:id/act` answer 403 to
  them, and `card.changed` goes out on the owner topic only (tested through the service, each route and the socket).
- The "needs your OK" screen has no `/oks` route: it is the orchestrator's `POST /api/m/orchestrator/stage/ok`,
  `/stage/ok/back` and `/stage/ok/finish` (and `GET /stage`), owner only (a member gets 403).

## 10. Known limitations

- **macOS host mode and the vault master key.** In `host` mode on macOS the vault master key lives in the owner's login keychain (7.3; never a `vault.key` file). The Seatbelt profile denies `~/Library/Keychains`, except that a Claude turn may read `login.keychain-db` (read-only): the Claude CLI keeps its own login there and reads it with `/usr/bin/security`, and without that file every sandboxed Claude turn is signed out. So a Claude agent's process can also ask the keychain for the PasaBot entry and read the master key; agents on other brains cannot read the keychain at all. macOS host mode is therefore for agents the owner trusts. The hardened deployments are Linux `user` mode and Docker (`container`), where the agent runs as another OS user or inside a container and has no way to ask for the key (both launchers land with W20; until then those modes refuse to run, 2.3). The server logs a one-line warning at startup in macOS host mode saying so. A native keychain helper (the key served only to the signed server binary, never to `security` calls from the agent sandbox) is planned in the late security pass (ROADMAP W27).

## 11. Machine linking (W28, after v1)

Several PasaBot servers owned by the same person (a laptop, a home box, a VPS) link to each other directly. There is **no vendor account and no central server**: each server stays the authority for its own agents, chats, vault and trust, and a link is a pinned-key relationship between two servers.

### 11.1 Packages

- `packages/link-transport`: the one interface every transport implements, plus the transports.

  ```ts
  export interface LinkStream extends Duplex {} // ordered, reliable bytes
  export interface LinkTransport {
    id: 'tailcat' | 'tcp-tls' | 'memory';
    /** our long-term public key (Ed25519), the address peers dial (a bearer secret), our tunnel key if any */
    identity(): Promise<{ publicKey: string; address: string; transportKey?: string }>;
    listen(onPeer: (s: LinkStream, peer: LinkPeer) => void): Promise<{ close(): Promise<void> }>;
    dial(address: string): Promise<{ stream: LinkStream; peer: LinkPeer }>;
    available(): Promise<{ ok: true } | { ok: false; installHelp: string }>;
    // optional, for transports with a tunnel of their own (tailcat):
    setAllowed?(transportKeys: readonly string[]): Promise<void>; // tunnel-level allow-list, takes effect at once
    openLinkWindow?(until: number): Promise<string>; // a short-lived address for link codes
    closeLinkWindow?(): Promise<void>;
    status?(): Promise<{ serving: boolean; restarts: number; linkWindow: boolean; version?: string }>;
    probe?(address: string): Promise<{ path: 'direct' | 'relay' | 'unknown'; rttMs?: number } | null>;
    close?(): Promise<void>; // stops every helper process
  }
  // LinkPeer = { publicKey; transportKey? (what the tunnel saw, inbound); viaLinkWindow? }
  ```

  - **Tailcat** (default): Tailscale's open-source BSD-3 netcat-style tool (userspace WireGuard + NAT traversal + DERP relays, no account). It is experimental with no API or CLI stability promise and Go only, so PasaBot never bundles, links or copies it: it drives the real `tailcat` v0.7 CLI as child processes (`spawn`, no shell, fixed argv from `TAILCAT_ARGV`), detects a missing binary and shows install help (Homebrew, `go install …@v0.7.0`, or the release binary with its checksum), and accepts `v0.7.x` (another version warns, never fails). How it is driven (each choice measured against v0.7.0):
    - **Keys**: two saved keys in the module's data dir (`tailcat/`, dir 0700, files 0600), always passed as `--key=<path>` so a user's own saved `default` / `client-default` keys are never picked up: a server key (`genkey --fixed-region`, so the address survives restarts) and a client key (`genkey --client`) whose `nodekey:<hex>` linked machines put in their `--allow`. Children get a minimal environment (no PasaBot secrets) with HOME / XDG / AppData pointed into that dir, so tailcat's relay-map cache stays there too.
    - **Listener**: one long-lived `tailcat --key=<server> serve --allow=<linked node keys> exec -- node -e <bridge>`, running **only while at least one machine is linked** (with nobody linked it would admit nobody, so nothing runs and nothing touches the relays; `listen()` only checks the CLI version and opens the loopback listener, and the server address is kept, 0600, from `genkey`). For each tunnel connection tailcat runs the tiny bridge, which connects to PasaBot's loopback-only TCP listener (127.0.0.1, port 0) and first sends a per-run token (from its environment, never argv) plus `$TAILCAT_PEER_KEY`; then it pipes both ways. `serve <port>` is not used because tailcat proxies to the _same_ port number on localhost, so peers would have to know a loopback port that changes at every start. The loopback port is **not a trust boundary**: the transport's key proof and the link handshake (pinned keys, code proof, protocol version) authenticate every connection exactly as over TCP+TLS; the token (it keeps other local users out) and `--allow` (the tunnel drops anyone else before a byte reaches PasaBot) are defence in depth. The allow-list is also re-checked per connection, so a removed key is refused at once while tailcat restarts. A `serve` that dies is started again with backoff (0.5 s doubling to 30 s).
    - **Dialer**: one long-lived `tailcat --key=<client> socks` child (loopback SOCKS5, OS-chosen port, stopped after 60 s idle); a dial is a SOCKS5 CONNECT to `<address>:1`, then the key proof, capped at 15 s. Not one `tailcat <addr>` process per dial: several client processes with one key at once break each other (one of three was reset after 16 s), and this way the address never enters an argv (`tailcat --key=x -- <arg>` would _run_ `<arg>` in server exec mode). Addresses must match `tc` + base64url, ≤ 255 chars, before anything else happens. A machine not in `--allow` is dropped silently by tailcat, after ~10 s, exactly like an unreachable one, so both show one error: "unreachable or does not admit this one".
    - **Status**: Settings → Machines shows the transport and whether its tunnel process runs; a check of a linked machine reports online/linked but no direct-or-relayed path: `tailcat ping` only takes the address on its command line, and the address is a bearer secret that other local users could read there (`ps`), so PasaBot never runs it (`probe` stays optional in the interface for transports that can answer without exposing the address). Children are tracked, one-shot commands included, and an unlinked machine's open tunnel connection is cut the moment its key leaves the allow-list. No helper process outlives `close()`, the PasaBot process (an exit hook) or, after a crash, the next start (pids are recorded and stale ones stopped).
  - **TCP+TLS** (fallback): a LAN or tailnet address; TLS with self-signed certs whose public key must equal the pinned key (no CA).
  - **Memory**: two transports in one process, for tests.
- `modules/link`: tables `link_peer` (id, name, public_key, grant `view|chat|manage`, transport, address_ref → vault, created_at, revoked_at), `link_code` (hash, expires_at, used_at), `link_intro` (offered introductions); owner REST; the machine switcher (web); collab tool bridge.

### 11.2 Linking flow

1. Machine A's owner opens Settings → Machines → Link a machine: A shows a **one-time link code / QR** (random 128-bit, expires in 10 minutes, single use; only its hash is stored). The code carries A's transport address and A's public-key fingerprint. Under tailcat that address is a **linking window**: a separate, short-lived `tailcat --key=new serve exec …` with a fresh ephemeral address and no `--allow` (the joiner's tunnel key is not known yet), open only while an unused, unexpired code exists and closed as soon as the code is spent or expires. A's long-lived address never appears in a code. Connections through the window are marked by the transport and may only carry a code-proven link request; anything else is refused.
2. Machine B's owner enters the code. B dials A, both run the **handshake**: protocol version + supported features, then each proves possession of its long-term key over a transcript that includes the code hash (so a replayed transcript or a code used on another link fails).
3. **Both owners confirm with re-auth** (password or passkey, W0b/W23 rules) on their own server, and A's owner picks the **grant** B gets: `view` (machine list, online state, agent names), `chat` (open chats with A's agents through B), `manage` (also the status of A's agents and starting/stopping A's routines, within A's own trust rules: a start fires as a `link` sender at most `standard`, never the owner, and a routine A's owner paused stays paused; stop pauses the routine and cancels its queued fires; a workflow only through a routine that targets it; never secrets such as prompts, trigger specs, instructions or workspace paths, never settings such as trust levels or grants). B's owner picks A's grant on B the same way. Grants are per direction.
4. Each side **pins the other's public key**. From then on only pinned keys may connect; the transport address is stored in the vault, never shown again in the UI and never logged (it is a bearer secret for the relay network). Under tailcat both sides also pin the other's **tunnel key** (client node key) during the code-proven link exchange: B's comes from tailcat itself (`$TAILCAT_PEER_KEY` of the window connection; a contradicting claim is refused), A's comes in its signed-handshake answer together with A's long-lived address. `link_peer.transport_key` holds it; each side's `--allow` lists exactly the tunnel keys of machines that are not unlinked, and a call whose tunnel key differs from the pinned one is refused. Unlink removes the key and restarts `serve` at once (open streams through that tunnel process drop; a peer's next request dials again).

### 11.3 After linking

- **Machine switcher**: the web app lists linked machines (name, online state, agents) and switches between them.
- **Proxied chats**: the browser always talks to its own server; that server forwards the chat end-to-end over the link to the remote server, which enforces its own auth and trust. A linked machine is **never an owner** there: its turns arrive as sender kind `link` with the trust the grant allows (at most `standard`, so tier 2+ always asks the remote owner), and remote approvals are answered on the remote machine.
- **Agents across machines**: the collab tools (message, delegate, wait) can address `agent@machine` when the grant allows it; trust = min of both agents and the link grant.
- **Introductions**: when a third machine links to one member, the member _offers_ introductions to the others (an approval to each owner); nothing links automatically.
- **Unlink** revokes the pinned key at once on this side and tells the peer; open streams are closed; queued proxied work is cancelled.

### 11.4 Threat model

| Threat                                                | Mitigation                                                                                                                                                                                                                                                                                |
| ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Stolen link code (photo of the QR)                    | 10-minute expiry, single use, hash only stored; linking still needs both owners' re-auth and the grant choice, so a code alone links nothing                                                                                                                                              |
| Replay of a handshake                                 | Transcript signed over both nonces + the code hash + protocol version; nonces are single use                                                                                                                                                                                              |
| Compromised linked machine                            | It holds only the grant it was given (never owner); its turns are capped at `standard` and tier 2+ asks the remote owner; unlink revokes at once; every proxied action is audited on the server that runs it                                                                              |
| Relay metadata (DERP sees who talks to whom and when) | Accepted and documented: the relay sees node keys, timing and sizes, never content; payloads are end-to-end encrypted (WireGuard with a pre-shared key under tailcat, TLS on the fallback); the address is never logged                                                                   |
| Leaked tailcat address (it holds the pre-shared key)  | A bearer secret: vault only, never logged, never in REST or events after linking, scrubbed from errors (tailcat's stderr, which prints it, is never forwarded). Even with it, `--allow` admits only linked machines' tunnel keys, and the link handshake still needs a pinned Ed25519 key |
| Local process on the loopback port                    | Not a trust boundary: a per-run token from the bridge's environment, the allow-list re-check, the key proof and the link handshake all apply; the dialer's loopback SOCKS port only reaches linked machines' tunnels, where the handshake needs our private key                           |
| Version skew                                          | The handshake exchanges protocol versions and refuses an unsupported one with a clear "update this machine" message; features are negotiated, never assumed                                                                                                                               |
| Tailcat breaking changes (experimental tool)          | Child processes behind `LinkTransport`, every argv in one table (`TAILCAT_ARGV`), `v0.7.x` accepted and others warned, a stub of the real CLI grammar for the contract suite, a gated live test against the real binary; the TCP+TLS fallback keeps linked machines usable                |

### 11.5 Proofs (done-criteria)

Two servers in one Vitest process over the in-memory transport (link, re-auth on both, pinned keys only, grants enforced, proxied chat under the remote server's own auth, cross-machine collab within the grant, introduction offered not applied, unlink refuses the next connection, replay and expired-code refusal, version-skew refusal); a contract suite every `LinkTransport` must pass; the same link flow over tailcat through a stub of the real v0.7.0 CLI (window address in the code, both tunnel keys pinned, a never-linked key refused, unlink drops the key); tailcat specifics against the stub (explicit `--key` in every argv, never an empty `--allow`, hostile addresses never reach an argv, the loopback port is not a way in, minimal child environment, restart with backoff, no process left). `PASABOT_LIVE=tailcat` runs the same transport against the real binary on one machine (skipped by default and in CI). A real run between two machines (macOS ↔ Linux over the public relays) was done by hand on 2026-11-14: both directions, a key not in `--allow` refused after ~10 s.

## 12. Planned safety, budget, memory and local-model rules (W31–W34, specified 2026-11-14, not built)

The workstreams are specified in ROADMAP ("W22 extension, W31–W38"); these are the architecture rules they must keep.

- **Kill switch (W31).** One server-side stopped flag (stored, read at boot before the queue dispatches) behind a core port `stopAll(actor, reason)` / `isStopped()`; the queue dispatcher, runner, workflow engine, routines and the browser, computer and voice modules check it before starting work and cancel what runs. Any actor may stop (owner, linked machine, channel command, automation token, agent); only an owner session with re-auth may resume. The stop writes a report of what it stopped. Built (iface, W31): `KillSwitch` in `@pasabot/core` ports (`ModuleHost.killSwitch`), core table `kill_switch` (one row), `apps/server/src/core/kill-switch.ts`; the dispatcher reads the flag on every tick (stopped: nothing leases, newly queued items are parked `held` with error `pasabot:stopped`, which a resume releases), a stop aborts running items as cancels (not shutdowns), and `resume(actor, { reauthed })` throws `KillSwitchError` `resume_forbidden` (any non-owner actor, 403) or `reauth_required` (401). The web shell renders the `topBarItems` slot in both top bars. A stop also expires every pending approval (`ApprovalServiceImpl.expireAllPending()`, listed in the report as kind `approval`), and the `/mcp` gateway checks the flag and that the run is still running again before each approval is asked, after it is answered and right before the handler, so an approval given during a stop never becomes an action. `GET /api/m/safety/state` gives the full report only to an owner session; every other principal gets `{ stopped, since }`.
- **Skill manifests (W31).** A skill's declared files / network / messaging / tools are enforced at run time by the runner and the `/mcp` gateway (undeclared use refused, not logged-and-allowed). The pre-install scan runs in a worker thread with a timeout; its output is advisory text for the owner, never a gate an agent can satisfy by rewording. Agent-installed skills carry the lowest trust in the chain (7.4). Built (iface, W31): `ToolRegistry.addGuard(ToolCallGuard)` / `refusal(call)`; the `/mcp` gateway runs every guard after input validation and before tiers, approvals and the handler (a refusal or a throw ends the call as a tool error), and refuses every call while the kill switch is stopped. A guard receives the call's resolved `actionClass`: guards run once with the static class before anything else, and again after a dynamic class (e.g. `tools_invoke`) is worked out. Only the owner widens a manifest: an agent's write that only narrows an approved manifest applies at once (lowest trust); a first manifest or a widening from an agent is stored as a proposal the owner approves or rejects, and the guard enforces only approved manifests. Gap: the skill binding is the queue payload `skill`, which no production path sets yet (the agent CLI picks synced skills itself), so enforcement covers only runs bound to a skill; a skill-bound run may not use work-starting tools (delegate, workflows, routines) or implicit-navigation tools (browser/computer click and type), and an outside MCP tool must be declared by its `server/tool` ref.
- **Receipts (W31).** Built from server-side events (run, tool call, approval decision with decider, screenshot ids, usage), never from the agent's own account of what it did; arguments pass the vault redaction before they are stored; export is redacted again and its HTML view is served only from the sandboxed sites origin.
- **Budgets (W32).** Costs come from `usage` events times the owner's price table; a missing price is "price not set", never estimated. A cap stops a run at a turn boundary or by cancelling cleanly (no half-applied tool call is retried); only the owner raises a cap.
- **Agent bundles (W32).** Authenticated encryption and a memory-hard KDF from a vetted library, versioned header, fail closed on a wrong passphrase or any tampering, paths checked before anything is written, import always creates a new agent at no more than the server default trust; vault entries only when the owner opts in (re-auth). The owner-approved W31 manifests of the agent's synced skills travel with it (`SkillManifestPort`); on import each one is a proposal the owner approves or rejects, at no more than the new agent's trust, never an approved manifest (a manifest equal to the approved one, or a skill with a pending proposal, is skipped).
- **Shared memory (W33).** Scopes global / team / private; provenance and trust set by the server from the writer's actor. Memory reaches a prompt only inside a labelled untrusted-data block. Deletion is propagated to every backend and to exports. No cloud sync unless the owner adds a backend that syncs.
- **Local models (W34, built).** `providers/local` (module id `local`, runtime providers `local:<endpoint id>`); safe-net's `classifyLocalModelUrl` (literal IP or `localhost` only, loopback or LAN, refuses public/metadata/names) and `fetchLocalModel(url, { allowed })` (exact allowed origins only, no redirects, streaming body, a fresh connection per request; a connect that does not finish within `connectTimeoutMs`, default 5 s, fails with code `ETIMEDOUT`, an idle socket after `timeoutMs`, default 120 s, with `ESOCKETTIMEDOUT`). The only safe-net exception: owner-configured loopback (and, with a warning, LAN) endpoints of kind `local-model`, used only by the local provider; agents and tools can never add or reach them through other tools. A fallback to a local model is said in the run's or routine's result.

## 13. Planned shopping and inbox rules (W30, W35, specified 2026-11-14, not built)

The workstreams are specified in ROADMAP (W30, W35); these are the architecture rules they must keep.

- **Store packs (W30).** `packages/store-packs` is data only: one schema-validated JSON file per country, found by discovery, each store with a stable `id`, a plain-text `name`, `homeUrl`, a `searchUrl` template with one `{query}` placeholder (filled URL-encoded, never adding parameters), `allowedHosts`, `currency` and `parsingHints` (structured-data preferences and plain CSS selector strings; never a regex or code). No logos or brand art, no affiliate or tracking parameters, no scraping service. The country default comes from the owner's locale/region, never an IP lookup or any network call; only the owner session switches country, toggles stores or adds a custom store. Module tables are prefixed `shop_` (settings, custom stores, captured products).
- **Browser port (W30, built as iface).** `ManagedBrowserPort` in `@pasabot/core` ports (`ModuleHost.browser`, set once by the browser module, `modules/browser/src/port.ts`): `read(actor, { profile?, url?, allowedHosts, selectors? })` returns the page's bounded JSON-LD texts, meta pairs, microdata pairs, the first match of each plain CSS selector and `signals` (`captcha`, `cardField`, `signIn`); `fill` refuses card, bank, password and one-time-code fields; `click` refuses any money action or a control on a payment page (the 7.1 detector); `handOver(actor, { reason })` leaves the browser open, marks the profile owner-driven and notifies the owner. Every address must be on the caller's `allowedHosts`, before and after navigation; the kill switch refuses every call. `profileInfo({ profile? })` says whether the profile may hold the owner's sign-ins (`loggedIn`), so a caller's agent tool takes tier 3 on such a profile like the browser tools' own `tierFor`; `read`/`fill`/`click` take the caller's `approvedTier` and refuse an `agent` actor on a signed-in profile below 3. Each port call's check and page action run under the profile's page lock (`BrowserManager.withLock`), the same lock the browser tools take, so a port navigation never lands between a tool's final check and its click, nor the reverse. Detached approvals may carry an always-ask `ask` card (`DetachedApprovalRequest.ask`), so a module's own owner action (the Buy button) gets the same money card as a tool call.
- **Captured products (W30).** Product facts are captured by the server from the page the W15 managed browser read and stored with their capture time; tools and blocks refer to a captured product id, never to an agent-typed price or link. Page data is untrusted: rendered as text, handed to the agent inside the labelled untrusted block. Images and links pass `safeImageSrc`/`safeHref` and must be on the store's `allowedHosts`. Prices are shown with "as seen at <time>".
- **Buy (W30).** `shop_buy` is `actionClass: 'money'` with `noAlwaysAllow: true`; its card (what, store, price with currency and capture time, quantity) comes from the captured product through `actionDetails`. After approval the agent may only open the approved product on an allowed host, add the approved quantity and open the cart/checkout page in the owner's own signed-in profile, then the run hands the live view to the owner, who pays. The approval binds that item, quantity and host; anything else money-class asks again (7.1 re-check); the final pay or place-order control, card and bank fields, OTPs, captchas, bot checks and account creation are never the agent's.
- **Inbox credentials and network (W35).** IMAP/SMTP host settings and the app password live only in the vault. Connections go through a safe-net TCP helper (`safeConnect` in `@pasabot/safe-net`: `onlyHosts` = the owner-entered hosts, `privateHosts` = operator config only, `requireTls()` before any credential): resolve, refuse blocked addresses, pin the resolved address, TLS required (implicit or mandatory STARTTLS), no plaintext authentication; the owner-entered hosts are allowed explicitly for that mailbox only, and no agent can add or change one. PasaBot never creates a mailbox, never signs in through a browser for the owner, and never solves captchas. Module tables are prefixed `inbox_`.
- **Guided email setup (ws/email).** For a named service (Gmail, Outlook, Yahoo, iCloud) the IMAP/SMTP servers are fixed in `modules/inbox/src/providers.ts`; a request can name only the service, the address and the code (a strict schema refuses any host), so an owner session cannot send a vault-held code to another server. The app password goes from `POST /api/m/inbox/connect` through the IMAP and SMTP sign-in check (safe-net, verified TLS before any credential) and only then into the vault (scope `inbox`); it is never echoed in a response, never logged (the log line carries the service and a reason code), never in an event, a table or the checklist state; the server's own refusal words are matched to a plain reason and dropped. The checklist (`app.config` key `guide`) holds no secret. Threat model: the helper (or any agent) never types, sees or receives the owner's email password or app password, never signs up, signs in, solves a captcha or a phone check, and never creates an account: those steps happen in the owner's own browser, opened through `safeHref` links to the service's own pages. The main helper's prompt context for the checklist says the same and that address ideas are only ideas. What helpers may do is the owner's choice (`read` / `draft` default / `send`); a tool guard refuses `inbox_send` and `inbox_bridge_send` unless it is `send` (fail closed: a missing or unknown value is no sending; a mailbox from before the choice existed is set to `draft` once at startup; a disconnect resets it to `draft`; any settings save with no choice yet sets `draft`), and then every email still waits for the always-ask outbound-message approval. Sign-in checks reach a real mail company, so `/connect` runs one at a time (a second gets 409 `busy`), at most 5 a minute, and pauses an address for 15 minutes after 5 refused codes (429 `too_many`); `/guide/check` (a full IMAP sync) runs one at a time, at most 10 a minute. The tiny test counts only a mail carrying the guide's own test word, dated from when the test step opened (10 minutes' clock leeway); it proves PasaBot can read the inbox, nothing more. Tests point the named services at a loopback fake mail server only through `serviceHosts` (constructor) or `PASABOT_INBOX_TEST_MAIL_SERVER` (operator config, loopback only).
- **Mail as data (W35).** Incoming mail is untrusted: shown as text on the Inbox page (HTML only inside the sandboxed origin, no remote images) and given to the agent only inside the labelled untrusted block through read-only tools. One-time codes, verification links and sign-in codes are masked before the agent sees them (a linear scan, no regex on the main thread); the owner sees them on the Inbox page. The scan counts short groups split by blank space, line breaks or dashes as one code (a code laid out one digit per box or HTML table cell, whose cells the HTML-to-text step ends with a space), hides a run of short groups longer than a code whole, hides the first group when the groups after it make the run too long, and on a line that names a code (or the line after one) also hides all-capital and lower-case letter-and-digit codes. Every send, reply or forward is `actionClass: 'outbound-message'` with to/cc/bcc, subject, body preview and attachments on the card.
- **Email bridge (W35).** Two paired PasaBot bots pin each other's sender address and Ed25519 public key (exchanged in the app). A bridged message carries a signed envelope over sender bot, recipient bot, thread id, nonce, timestamp and body hash; the receiver refuses a wrong key or From address, a reused nonce, a timestamp outside a short window, and any unsigned or altered envelope. A verified message is still untrusted data, and each reply still asks.
